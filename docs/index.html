The two rules that shape everything

One decider. Deny by default.

Rule 01 Only one component says yes or no

The risk engine emits weighted signals and nothing else. OPA is the single Policy Decision Point. A test fails if the word BLOCK ever appears in the risk module — two things that can both deny will eventually disagree, and then nobody can explain a stopped payment.

Rule 02 Absence of a decision is never a yes

No policy bound, OPA unreachable, the classifier timed out, the revocation set unreadable, an unhandled exception — each resolves to BLOCK. When the LLM classifier is down and the deterministic layers are clean, the payment goes to a human, not through.

How a payment is judged

Seven stages, in the order the gateway runs them

  1. Identity & request integrity
    Confirms the agent is who it claims to be and still allowed to act.
    Delegation JWT signature · agent scope · revocation-set lookup · token-to-intent binding
  2. Canonical transaction
    Freezes the money-moving fields as a typed record. Every free-text field is quarantined in one untrusted bag so no later stage mistakes it for an instruction.
    Amount, merchant, currency, cart-hash typed once · purpose & page text isolated
  3. Content analysis
    Scans the untrusted text for attempts to manipulate the agent. Three layers, combined by taking the strongest — not the average.
    Regex rules · character-shingle + intent-cluster similarity · LLM classifier · source-trust weighting
  4. Risk scoring
    Turns facts and evidence into a weighted score. Produces signals only — it never returns a verdict.
    35·injection + 25·policy + 20·budget + 10·merchant + 10·velocity
  5. Policy decision
    Open Policy Agent applies the written policy and returns exactly one of ALLOW · REQUIRE_APPROVAL · BLOCK. The only component that decides.
    Rego bundle · amounts compared as integer minor units · fails closed if OPA is unreachable
  6. Payment authorization
    Issues a scoped, single-use token bound to this exact cart, then drives a payment state machine. Never reached on a BLOCK.
    One-time token · CREATED → AUTHORIZED → SUBMITTED → CONFIRMED · UNKNOWN is reconciled, never retried
  7. Immutable audit
    Writes a tamper-evident record of the outcome — allows and approvals as well as blocks — and anchors the chain head in an independent store.
    SHA-256 hash chain · second database, separate credentials · verify names the first broken link

The trust boundary

The gateway cannot grant itself authority

Registering agents, binding policies, and minting delegation tokens is a different trust domain from enforcing a payment. It runs as a separate service behind an admin key, and it is the only holder of the delegation private key. In the deployed stack the gateway container is not given that key at all.

The agent is real

A CrewAI crew whose only way to spend is this gateway

A shopper and an independent reviewer, orchestrated by LangGraph, with a toolset of exactly product_search, fetch_merchant_page, and propose_payment_intent. There is no charge_card, no provider client, no stored credential. Three properties are enforced by structure and pinned by tests:

  • One money-moving tool — a second payment path fails the suite.
  • “Blocked” is terminal — no graph edge leads back to the payment nodes, so the agent cannot resubmit a smaller amount to negotiate with the policy engine.
  • The injection reaches the agent byte-for-byte — its SHA-256 is recorded at the tool boundary, because a block only proves something if nothing upstream sanitised the attack first.

Stated plainly

What it does not yet do

A security system that oversells itself is worse than one that doesn’t.

  • The payment rail is a mock. The enforcement layer is provider-agnostic; a real Razorpay test-mode Order gated at pre_checkout_query is roughly a day of adapter work, not an architecture change.
  • X-Admin-Key is a shared secret. The door exists and is shut by default; a real deployment puts SSO or mTLS and per-operator identity there.
  • Postgres and Redis are single-node in the payment path. Fail-closed keeps it safe, not available; the HA plan is a read replica for revocation, OPA as a sidecar, a Postgres standby.
  • The signing keys are static files. The trust domains are already split; a real deployment signs in a KMS and no private half touches a filesystem.
